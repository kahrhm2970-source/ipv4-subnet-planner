# IPv4 Subnet Planner

An offline Python CLI for reviewing an IPv4 subnet inventory: masks, host ranges, address counts and overlapping networks. Prepared with AI assistance for **Alhussin Ali Abutalib's** Network Technician / IT Support portfolio.

## Problem and outcome

A proposed VLAN address plan can contain overlapping ranges or incorrect network boundaries. This tool checks the supplied inventory before a technician copies it into a deployment plan. It produces JSON suitable for documentation. It does not allocate subnets automatically or configure equipment.

## Requirements and implementation

Python 3.10+; standard library only (`ipaddress`, `json`, `argparse`, `unittest`). No installation, API key, credentials or network access required.

```bash
git clone https://github.com/kahrhm2970-source/ipv4-subnet-planner.git
cd ipv4-subnet-planner
python subnet.py example.json
python -m unittest -v
```

Optionally save stdout to a **new** filename:

```bash
python subnet.py example.json > my-report.json
```

Shell redirection overwrites files; choose the destination carefully.

## Input and validation

Input is a UTF-8 JSON array of 1–256 strings. Each string is an explicit IPv4 network with a slash and a valid prefix or supported netmask. Host bits must be zero (`192.0.2.1/24` is rejected). IPv6, duplicate networks and malformed values are rejected. Files with a UTF-8 BOM are accepted.

```json
["192.0.2.0/25", "192.0.2.128/26", "192.0.2.192/26"]
```

These are documentation addresses, not a real customer network. The program accepts other IPv4 ranges for arithmetic; acceptance does not mean that the range is suitable for deployment.

## Output and example results

See [example-report.json](example-report.json), generated by the CLI.

| CIDR | Mask | First host | Last host | Host count |
|---|---|---|---|---|
| 192.0.2.0/25 | 255.255.255.128 | 192.0.2.1 | 192.0.2.126 | 126 |
| 192.0.2.128/26 | 255.255.255.192 | 192.0.2.129 | 192.0.2.190 | 62 |
| 192.0.2.192/26 | 255.255.255.192 | 192.0.2.193 | 192.0.2.254 | 62 |

Result: `NO_OVERLAP_IN_INPUT`. Nested ranges are reported as overlap; adjacent ranges are not. Overlap can be intentional in a routing hierarchy, so findings require context.

For conventional subnets, host count excludes the network and broadcast addresses. `/31` uses point-to-point semantics with two addresses; `/32` represents one host. `last_address` is the numerical upper endpoint, not a claim that `/31` or `/32` uses a broadcast address. The program does not enumerate every host, even for `/0`.

Exit codes: **0** no overlap in supplied inventory; **1** overlap found; **2** invalid input or file read error. No overlap does not prove that addresses are unused elsewhere.

## Validation performed

Ten automated tests passed locally on 11 November 2026, covering `/24`, `/30`, `/31`, `/32`, `/0`, nested overlaps, adjacent networks, invalid inputs, duplicates and input shape/size. The CLI produced the included example report. These are software checks; no live network or physical equipment was tested.

## Workflow

Validate inventory → calculate subnet details → compare each pair for overlap → print JSON.

## Lessons and career relevance

This exercise connects subnetting fundamentals to Python automation, boundary testing, input validation and technical handover. A key lesson is to treat `/31` and `/32` explicitly rather than applying the conventional host formula everywhere.

## Limits and privacy

No live discovery, reachability tests, duplicate-IP detection, routing validation, VLAN configuration, DHCP exclusions, reserved-address policy, VLSM allocation or IPv6 support. Review gateway/reserved addresses, organization policies and existing inventories independently. Publish only synthetic examples; never upload credentials, real customer addressing, configurations or private topology files. `.gitignore` is not a secret scanner.
